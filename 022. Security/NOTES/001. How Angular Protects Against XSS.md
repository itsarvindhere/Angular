XSS (cross-site scripting) is when an attacker gets their own script to run inside your page, for example through a comment, a profile name or a URL parameter. Angular is built to make this hard.

The idea is simple - Angular treats every value as untrusted by default. Before a value goes into the DOM through a template binding or interpolation, Angular sanitizes it or escapes it.

# INTERPOLATION IS ALWAYS ESCAPED

    <p>{{ comment }}</p>

If "comment" contains "<script>alert('hacked')</script>", the user just sees that text on the screen. It is never run as HTML.

# [innerHTML] IS SANITIZED

Sometimes we really do want to render HTML, for example a blog post written by someone. For that we use property binding -

    <div [innerHTML]="postHtml"></div>

Angular sanitizes the HTML. It removes dangerous things like "<script>" but keeps safe markup like "<b>" and "<p>". In development mode, Angular also logs a console warning when it had to change a value.

# THE SECURITY CONTEXTS

Angular treats different places in the DOM differently. These are called "security contexts" -

 - HTML - for example "[innerHTML]"
 - Style - for example the "style" property
 - URL - for example "<a [href]>"
 - Resource URL - for example "<script [src]>" or an iframe "src"

Angular can sanitize HTML and URLs. It cannot sanitize a Resource URL, because that one loads and runs code, so such bindings need extra care.

# TEMPLATES ARE TRUSTED CODE

Angular treats your templates as trusted. So -

 - Never build a template by joining strings that contain user input.
 - Use the AOT compiler in production (the default for "ng build"). JIT compiles templates in the browser at runtime, which is a security anti-pattern when templates contain user data.
 - Do not generate Angular templates on the server with a templating language.

You can read more on the official Angular website - https://angular.dev/best-practices/security
