XSRF (also called CSRF) is when another website tricks the browser of a logged-in user into sending a request to your server. If your app uses cookies for login, the browser attaches the cookie automatically, so the server cannot tell the difference.

A common defence is a token that only your own site can read and send back. Angular's "HttpClient" supports this out of the box, but only the client half -

 1. The server sets a cookie named "XSRF-TOKEN".
 2. "HttpClient" reads that cookie and sends its value in the "X-XSRF-TOKEN" header.
 3. The server checks that the header matches the cookie. Angular does not do this part, your server must.

Details -

 - It is sent only for mutating requests (like POST, PUT, DELETE) and only to relative or same-origin URLs.
 - GET and HEAD requests are not covered.

# CHANGING THE NAMES

If your server uses different names -

    provideHttpClient(
        withXsrfConfiguration({
            cookieName: 'CUSTOM_XSRF_TOKEN',
            headerName: 'X-Custom-Xsrf-Header',
        }),
    )

# TURNING IT OFF

    provideHttpClient(withNoXsrfProtection())

# DOES THIS APPLY TO OUR AUTH PROJECT?

Our Recipe project sends the Firebase token as a query parameter ("?auth=..."), not as a cookie, so the browser does not send it automatically and classic XSRF does not apply. It becomes relevant when you move to cookie-based sessions.

You can read more on the official Angular website - https://angular.dev/best-practices/security
