**Status: developer preview. The Angular docs mark router error boundaries as being in developer preview.**

In the Error Handling section we learned that an unexpected error goes to the global "ErrorHandler". That is good for logging, but the user may be left looking at a broken page.

A router error boundary catches errors from the component of a route and shows a fallback component instead.

# TURNING IT ON

    provideRouter(
        routes,
        withErrorBoundaries({
            defaultErrorComponent: GlobalErrorFallback,
            onError: (error, details) => { /* log it */ },
        }),
    )

 - "defaultErrorComponent" - the fallback used by every route that does not have its own.
 - "onError" - a function that is called with the error, for example to log it.

# A FALLBACK FOR ONE ROUTE

    { path: 'recipes/:id', component: RecipeDetail, errorComponent: RecipeError }

The "errorComponent" must be loaded eagerly, so you cannot use "loadComponent" for it.

# THE FALLBACK COMPONENT

It receives the error through an input -

    export class RecipeError {
        readonly error = input<Error>();
    }

With "withComponentInputBinding()", the route params and static data also bind to the inputs of the fallback. If one of them is called "error", the caught error wins.

# WHAT IT CATCHES

 - Errors in constructors, dependency injection, lifecycle hooks and template expressions.
 - Errors in the loaders of resources that live inside the component.

# WHAT IT DOES NOT CATCH

 - A failing guard ("canActivate", "canMatch") or a failing "resolve" function. These are navigation errors, and you handle them with "withNavigationErrorHandler".

# GOOD TO KNOW

 - Throwing a "RedirectCommand" navigates the user. If the route has no error component, the redirect is swallowed and does not reach the "ErrorHandler".
 - If the fallback component itself throws, that error bubbles up to the root "ErrorHandler".

You can read more on the official Angular website - https://angular.dev/guide/routing/error-boundaries
