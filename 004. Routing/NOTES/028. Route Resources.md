**Status: developer preview. The Angular docs mark route resources as being in developer preview, so the API can still change. Resolvers (the "Resolve" note earlier in this section) are not deprecated.**

In the Resolve note we saw that a resolver loads data before the route is shown. That works, but it has limits - resolvers run one after another from parent to child, and the navigation is blocked until they finish.

Route resources solve the same problem with the Resource API from the Signals section. They are declared on the route, they run in parallel, and they can reload without navigating again.

# TURNING IT ON

    provideRouter(routes, withComponentInputBinding(), withRouterResources())

# DECLARING A RESOURCE

The route property is called "resources" (plural). It is a function that gets a context and returns an object of resources -

    const routes: Routes = [
        {
            path: 'user/:id',
            component: UserProfile,
            resources: (ctx) => {
                const userService = inject(UserService);
                return {
                    user: resource({
                        params: () => ctx.params()['id'],
                        loader: ({ params: id }) => userService.getUser(id),
                    }),
                };
            },
        },
    ];

The function runs in an injection context, so "inject()" works inside it. It can be async, and it can return an "rxResource" (which uses "stream" instead of "loader") or any other "Resource".

# READING IT IN THE COMPONENT

By default the resource is "blocking". The router waits for it, and then binds the loaded value to an input with the same name. The input type is the plain value, not a "Resource" -

    export class UserProfile {
        user = input.required<User>();
    }

# WHAT RE-RUNS IT

The resource re-runs when a signal that it reads in "params" changes. For example, a query parameter -

    params: () => ctx.queryParams()['category']

Changing a different query parameter does not trigger a new load. One tip from the docs - read the specific value ("ctx.params()['id']"), not the whole "ctx.params()" object, because the router creates a new object on every navigation.

You can also reload by hand, with ".reload()" on the resource. You get it from "inject(ActivatedRoute).resources?.['user']".

# NON-BLOCKING RESOURCES

If you do not want to hold the navigation back, wrap the resource in "nonBlocking()" -

    user: nonBlocking(resource({ ... }))

The page shows immediately, and the component gets a real "Resource<User>" so it can use "isLoading()", "error()", "hasValue()" and "value()".

# ERRORS AND REDIRECTS

 - A blocking resource that fails cancels the navigation and emits a "NavigationError".
 - A non-blocking resource that fails puts the error in its own "error()".
 - Throwing a "RedirectCommand" inside a loader redirects the user.

# PARALLEL AND DEPENDENT LOADING

Resources of all the matched routes (parent and child) start at the same time. The docs' example - resolvers of 200ms and 300ms take 500ms in total, while resources take about 300ms.

If a child really needs a parent's data, chain them. The context gives you the parent resources through "ctx.resources()", and "chain()" connects them -

    params: ({ chain }) => chain(ctx.resources()['user'] as Resource<User>).role

Do not call or destructure "ctx.resources()" in the body of the outer function, only inside "params". If the parent fails, the error reaches the child as a "ResourceDependencyError".

Resources are inherited. "ActivatedRoute.resources" gives the route's own resources plus those of its parents, and a child resource with the same name hides the inherited one.

# RESOURCES OR RESOLVERS?

The docs do not say that resolvers are going away. They suggest resources if you already use signals, and if the child routes do not depend on the parent's data. Resolvers are still fine, and they are stable.

You can read more on the official Angular website - https://angular.dev/guide/routing/data-fetching-with-resources
