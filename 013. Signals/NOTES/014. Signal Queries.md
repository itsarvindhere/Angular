In the Components section, we learned how to get a reference to an element or a child component using decorators like @ViewChild(), @ViewChildren(), @ContentChild() and @ContentChildren().

Just like Signal Inputs replaced @Input(), we now have "Signal Queries" which are functions that replace these decorators. They have been stable since Angular 19.

| Decorator              | Signal Query        |
|------------------------|---------------------|
| @ViewChild()           | viewChild()         |
| @ViewChildren()        | viewChildren()      |
| @ContentChild()        | contentChild()      |
| @ContentChildren()     | contentChildren()   |

# TRADITIONAL APPROACH

    @ViewChild('nameInput') nameInput!: ElementRef<HTMLInputElement>;

    ngAfterViewInit() {
        this.nameInput.nativeElement.focus();
    }

We had to wait for the "ngAfterViewInit" hook because the element is not available before that.

# SIGNAL QUERY APPROACH

    nameInput = viewChild<ElementRef<HTMLInputElement>>('nameInput');

The result is a Signal. So, to read it, we call it like a function -

    this.nameInput()?.nativeElement.focus();

Since the element may not exist yet (or may not exist at all, for example if it is inside an @if block), the value of this signal can be "undefined". That's why we used the optional chaining operator above.

If we know for sure that the element will always be there, we can use "viewChild.required()" -

    nameInput = viewChild.required<ElementRef<HTMLInputElement>>('nameInput');

Now, the type does not include "undefined". But if the element is not found at the time we read the signal, Angular throws an error.

# QUERYING A COMPONENT OR DIRECTIVE

Just like before, we can pass a class instead of a template variable name -

    child = viewChild(ChildComponent);

And if we want something other than the default token, we can use the "read" option -

    nameInput = viewChild('nameInput', { read: ElementRef });

# VIEWCHILDREN AND CONTENTCHILDREN

The plural versions give us a Signal with a read-only array -

    items = viewChildren(ItemComponent);       // Signal<readonly ItemComponent[]>
    projected = contentChildren(TabComponent); // Signal<readonly TabComponent[]>

Note that this is not a "QueryList" anymore. We get a plain array, so we can use normal array methods like map() and filter() on it.

# VIEW QUERIES VS CONTENT QUERIES

The difference is the same as before.

    - viewChild() and viewChildren() look inside the component's own template.
    - contentChild() and contentChildren() look at the content that is projected into the component using <ng-content>.

One small difference to remember: by default, contentChild() looks at all descendants, while contentChildren() looks only at direct children. You can change that using the "descendants" option.

    tabs = contentChildren(TabComponent, { descendants: true });

# WHY ARE THEY BETTER?

    1. No need to wait for a lifecycle hook like ngAfterViewInit or ngAfterContentInit just to read the value.
    2. Because the result is a signal, we can use it inside computed() and effect() and they will automatically update when the query result changes.
    3. The types are more accurate, since the "required" version and the optional version have different types.

For example, we can derive a value from the query result -

    items = viewChildren(ItemComponent);
    itemCount = computed(() => this.items().length);

# TOUCHING THE DOM

If we need to do some work on the DOM element (like focusing it), then we should do it after Angular has rendered the component. For that, we can use the "afterNextRender" hook that we saw in the Lifecycle section -

    constructor() {
        afterNextRender(() => {
            this.nameInput()?.nativeElement.focus();
        });
    }
