SSG or "Static Site Generation" is also referred to as "Pre-rendering". It is a method of generating static HTML pages at build time. This means that the HTML for each page is generated when the application is built, rather than at runtime when a user requests the page. This can lead to faster load times and improved performance, as the server does not need to generate the HTML on each request.

So, we get the same performance benefits as SSR, but we also get a reduced Time to First Byte (TTFB).

The key distinction versus SSR lies in the approach that pages are served as static content, and there is no request-based rendering.

If all the pages are pre-rendered then you can use a static web server. This can lead to significant cost savings compared to using a server that needs to render pages on demand.

Otherwise, you have to use a dynamic web server just as in case of SSR.

The potential disadvantage of SSG is that there is no dynamic server-side data fetching. Let's say we pre-render a page that fetches data. That data will be fetched during the build process and will be static. If the data changes, the page will not reflect those changes until the next build. So, until the next build, the page might show outdated data.

If you added SSR to your Angular app, you will see that in "app.routes.server.ts", by default, there is a single entry for all the routes ("**") with the render mode "RenderMode.Prerender". It means Angular tries to pre-render all the pages at build time.

By default, Angular looks at the router configuration and sees what all routes are there that do not have dynamic route parameters (For example, product/:id, where id is dynamically provided) in their path. Then it will pre-render those pages. It makes sense because Angular does not know what the value of 'id' or any other dynamic route parameter is at build time. So, it cannot pre-render that page (unless we tell it the values, as we will see).

If you run "ng build" command then you will see that in the terminal, it will tell you how many routes were pre-rendered (in our project, it says "Prerendered 2 static routes."). In our project, you will see in the "dist/ssr-final" folder there will be a file named "prerendered-routes.json" which will show all the routes that are pre-rendered.

# SERVER ROUTES (app.routes.server.ts)

The "app.routes.server.ts" file is where we decide how each route is rendered. It has an array of "ServerRoute" objects and for each of them, we set a "renderMode" -

    export const serverRoutes: ServerRoute[] = [
        {
            path: '',
            renderMode: RenderMode.Prerender    // SSG - rendered at build time
        },
        {
            path: 'about',
            renderMode: RenderMode.Prerender
        },
        {
            path: 'profile',
            renderMode: RenderMode.Server       // SSR - rendered on every request
        },
        {
            path: 'dashboard',
            renderMode: RenderMode.Client       // CSR - rendered in the browser only
        },
        {
            path: '**',
            renderMode: RenderMode.Server       // all the other routes
        }
    ];

So, we get all the three rendering methods (CSR, SSR and SSG) in the same application, and we choose what is best for each page. For example, a static page like "about" is a good fit for SSG, a page with user-specific data like "profile" needs SSR and a page that is behind a login and does not need SEO can be CSR.

# PRE-RENDERING ROUTES WITH PARAMETERS

Let's say we want to pre-render the routes for "product/:id" for the "id" values 1 and 2. That is, we want to pre-render the following routes:

    /product/1
    /product/2

We can do that using the "getPrerenderParams" function of the route, which tells Angular which values to pre-render -

    {
        path: 'product/:id',
        renderMode: RenderMode.Prerender,
        async getPrerenderParams() {
            return [{ id: '1' }, { id: '2' }];
        }
    }

This function can also be "async" so we can fetch the ids from an API or a database at build time. Only these pages are pre-rendered. Since we have not changed the other entries, they work as before.

# THE "outputMode" OPTION

Finally, the "outputMode" option in angular.json decides what is generated by the build -

 - "server" (our project): We get a server that can render the pages (SSR) along with the pre-rendered pages. This is required if any of our routes uses "RenderMode.Server", or if we have our own REST API endpoints in the server.ts file.
 - "static": We get only static files (HTML, JS, CSS) and no server. This can be deployed on any static hosting like Amazon S3. For this, all the routes should be either pre-rendered or client-side rendered.

# THE OLDER "prerender" OPTION

Before the server routes, the pre-rendering was configured only in angular.json using the "prerender" property under "build" options (you may still see it in older projects). It can be a boolean (all the routes without parameters are pre-rendered) or an object with these properties -

    1. discoverRoutes - Whether the builder should process the Angular Router configuration to find all unparameterized routes and pre-render them. The default value is 'true'.
    2. routesFile - The path to a file that contains a list of all routes to pre-render, separated by newlines. This option is useful if you want to pre-render routes with parameterized URLs.

For example, with a "routes.txt" file in the root of the project having these two lines -

    /product/1
    /product/2

We could do this -

    "prerender": {
        "routesFile": "routes.txt"
    }

But the server routes approach above is more flexible as we can choose the render mode for each route, so that is what is used in the new projects.
