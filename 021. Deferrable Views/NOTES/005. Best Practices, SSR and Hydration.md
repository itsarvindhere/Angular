# BEST PRACTICES

1. Avoid cascading loads with nested @defer blocks.

When we have a @defer block inside another @defer block, they should have different triggers. If both use the same trigger (for example "on immediate"), the inner one will start loading as soon as the outer one finishes, which causes a chain of requests one after the other and can slow down the page.

2. Avoid layout shifts.

Avoid deferring components that are already visible in the viewport when the page loads. When the placeholder is replaced by the real content, the page can jump, which hurts the Core Web Vitals (specifically the "cumulative layout shift").

If you really have to do it, avoid the triggers that load the content during the initial page render, such as "on immediate", "on timer", "on viewport" and a custom "when" condition.

# @defer WITH SERVER-SIDE RENDERING (SSR)

By default, when the app is rendered on the server (SSR or SSG), the @defer blocks always render only their @placeholder (or nothing if there is no placeholder) and the triggers are not run. On the client, the placeholder is hydrated and then the triggers are activated.

This also means that the real content of the @defer block is not in the server-rendered HTML. If we want that, we can use "Incremental Hydration".

# INCREMENTAL HYDRATION

Incremental hydration lets the server render the main content of a @defer block (not the placeholder), but the browser keeps it "dehydrated" (not interactive yet) and does not download its JavaScript until a "hydrate" trigger fires. Because the real content is already in the HTML, it also lets us defer content that is above the fold without a layout shift.

In Angular 22, incremental hydration is enabled by default, so "withIncrementalHydration()" is deprecated and no longer needed. In older versions, we had to add it to the hydration providers -

    provideClientHydration(withIncrementalHydration())

Then, add a "hydrate" trigger to the @defer block -

    @defer (hydrate on viewport) {
        <some-large-component />
    } @placeholder {
        <div>Large component placeholder</div>
    }

The available triggers are the same as the normal ones, prefixed with "hydrate" - "hydrate on idle", "hydrate on viewport", "hydrate on interaction", "hydrate on hover", "hydrate on immediate", "hydrate on timer(500ms)" and "hydrate when condition". We can separate multiple triggers with a semicolon and hydration will start when any of them fires.

There is also "hydrate never" which keeps the content as static, never hydrated content. It also stops the hydration of everything nested inside that block -

    @defer (on viewport; hydrate never) {
        <some-large-component />
    }

Hydrate triggers are used alongside the normal triggers. Hydration is only an optimization of the initial load, so the "hydrate" triggers apply only to the content that came from the server. Any later client-side render uses the normal trigger -

    @defer (on idle; hydrate on interaction) {
        <some-large-component />
    } @placeholder {
        <div>Large component placeholder</div>
    }

If the user clicks (or does another event that the component listens to) before the hydration is done, Angular saves that event and replays it once the hydration finishes, so the interaction is not lost.

Finally, for nested @defer blocks, hydrating a child also needs its parents to be hydrated. So Angular hydrates from the top-most dehydrated @defer block down to the child.

Note that a "hydrate when" condition only works for the top-most dehydrated @defer block, because the condition lives in the parent component, which may not be hydrated yet.
